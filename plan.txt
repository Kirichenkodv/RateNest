idea:
Backend (API) для сбора обратной связи от клиентов детского центра.
Пользователь (родитель) входит максимально просто — по коду на телефон/email или через Telegram/VK —
и оставляет обращение: отзыв, вопрос или предложение, адресованное владельцу или конкретному преподавателю.
Читает обращения только владелец бизнеса.
Учебный проект для закрепления навыков Python/Django и работы «как в реальной команде».

предметная область:
- центр один, преподавателей немного
- обращение (Feedback):
  - тип: отзыв / вопрос / предложение
  - адресат: владелец или конкретный преподаватель
  - оценка 1–5 (только для отзыва)
  - текст, автор, дата, статус (новое / прочитано)
- обращения приватные: автор видит свои, владелец — все
- ответы на обращения — пока под вопросом (backlog)

вход / регистрация (регистрация = первый вход, без паролей):
- телефон + одноразовый код (SMS-провайдер — абстракция, реализация фейковая: код пишется в лог; платные SMS не используем)
- email + одноразовый код
- Telegram Login Widget
- Telegram-бот, присылающий код / deep-link
- VK ID (OAuth 2.1 + PKCE)
- Госуслуги — НЕ берём: нужна регистрация юрлица в ЕСИА
- после входа — JWT (access + refresh)
- несколько способов входа привязываются к одному аккаунту

stack:
- python, uv
- django + django-modern-rest (dmr) — осознанно, изучаем
- postgresql, redis (одноразовые коды, rate limiting)
- docker compose
- pytest + pytest-django
- ruff, mypy
- pre-commit
- ci-cd: GitHub Actions, деплой на VPS
- OpenAPI (генерирует dmr) + коллекции insomnia

процесс (максимально близко к реальной команде):
- вехи = GitHub Milestones, задачи = GitHub Issues (с метками: feature / infra / bug / chore)
- агент на каждую задачу:
  - создаёт issue: контекст, требования, критерии приёмки, подсказки (без готового кода)
  - создаёт ветку feature/<номер>-<название> с падающими тестами (TDD)
- я:
  - пишу код в этой ветке, пока тесты не станут зелёными
  - открываю PR по шаблону, ссылаюсь на issue (Closes #N)
- проверки на PR:
  - CI: ruff, mypy, pytest, сборка docker-образа — обязательны для merge
  - code-review агентом в GitHub Actions (claude-code-action), комментарии inline,
    с пометками [blocker] / [suggestion] / [nit] и объяснением «почему»
  - main защищён: без зелёного CI и approve мержить нельзя
- исправляю замечания, пушу, ревью повторяется
- merge через squash, коммиты в стиле Conventional Commits
- если застрял — агент даёт наводящие вопросы и подсказки, а не готовое решение

вехи:
0. Фундамент
   - uv-проект, Django + dmr, настройки через env
   - docker compose: app + postgres + redis
   - ruff, mypy, pre-commit, pytest
   - healthcheck-эндпоинт
   - CI в GitHub Actions, шаблоны issue/PR, защита main
1. Домен и админка
   - модели Teacher, Feedback, миграции
   - Django admin для владельца (просмотр, фильтры, отметка «прочитано»)
2. Пользователь и JWT
   - кастомная модель User (телефон / email / telegram_id / vk_id — все опциональны)
   - выдача и обновление JWT, эндпоинт /me
3. Вход по одноразовому коду
   - общая абстракция OTP: генерация, хранение хеша в redis, TTL, лимит попыток, rate limiting
   - телефон (фейковый SMS-провайдер) и email
4. Деплой
   - prod-Dockerfile, gunicorn/uvicorn, reverse proxy (caddy/nginx), HTTPS
   - CD: при merge в main — сборка образа и деплой на VPS
5. API обращений
   - создать обращение, список своих
   - для владельца: список с фильтрами и пагинацией, отметка «прочитано»
6. Telegram
   - Telegram Login Widget (проверка подписи)
   - бот: вход по коду / deep-link
   - уведомление владельцу о новом обращении
7. VK ID
   - OAuth 2.1 + PKCE
   - привязка нескольких способов входа к одному аккаунту
8. Документация API
   - OpenAPI, коллекция insomnia, README

backlog:
- ответы владельца на обращения
- логи и мониторинг (Sentry)
- интеграция с другим моим проектом
